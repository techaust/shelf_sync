**Corrections to earlier assumptions:**
1. **One test site, and the app can't reach it.** Twins and near misses can't be integration-tested on Laragon. They're proven by contract tests (fakes built from the docs, RFC 2606 hosts) and by L1 on the live stores. Test-stack proofs are pytest runs through a transport seam using `testenv.laragon`'s transport (Q1, Q2).
2. **The samples' download names.** `testenv/samples.py` names each download after its file; on the real stores the main one is "Download" (OmniSync's `PRIMARY_NAME`, and 03 CAT-05's default). m3.1 renames the samples' main downloads, then Claude re-runs `seed`.
3. **The client's 1 MiB cap** (`apply/woocommerce.py`) is sized for Test connection, not for a 100-product page with `downloads` and `meta_data`. Each call gets its own cap: 8 MiB proposed (`seed` uses 4 MiB); the real page size is measured at L1.
4. **APL-12 retries GETs only in M3.** Retrying a write after a 5xx or 52x can repeat a write that already landed; M5 decides write retries with APL-03 and APL-10. A test refuses any retry of a non-GET.
5. **Stale `latest_version_<x>`.** OmniSync writes `latest_version` plus `latest_version_<mapping slug>`, and the mapping slug comes from the attached file, so "differs from the URL slug" would flag most products. Proposed rule: `<x>` matches no current download's file stem on that product. L1 counts each form before the rule ships; the removal itself is APL-09 (M5).
6. **Only local fixes get a button in M3:** link a pair, "not the same", dismiss, accept (SYNC-02) and the slug edit (CAT-04 M3). Fixes that write to a store (remove a stale key, restore) show their reason and suggested fix, with no button until M5.
7. **Near-miss titles.** The research script drops edition words; the app keeps them ("X Pro" and "X" are different products) and adds `html.unescape`. L1 confirms the 3 pairs still appear.
8. **Cookie text in the log** (10-status follow-up, an `http.cookiejar` warning) becomes likely at about 25 pages per read. m3.1 fixes it before L1.

### m3.1-catalog-read [CAT-01, CAT-02, CAT-03 (detection), CAT-04 (slug), CAT-05, APL-12 (GET), ERR-02 (backend)] · Tier B, plus `security-review` (it touches `apply/`, 12 §2)

## 4. Risks and unverified points
**Still "to verify" in 04-A:** V3 (the download ID kept on update; m3.2, test site); V28 (`include_status`'s minimum version, and whether `any,trash` works as one value; m3.2; it could raise CAT-01/ERR-02's 5.8 floor); V1 and V27 on the test site (m3.1); V2 rests on a secondary source only; V30 re-counted at L2 (if variations appear, the lead re-plans).

**Real-data unknowns (L1 settles them):** the page size with `meta_data`; the main-download names and how the two multi-download products pair; the `latest_version_*` forms and the stale rule; how many duplicates, and what "duplicate" means (03 doesn't define it); HTML entities in titles; changes since 2026-10-25 (the exit test compares against L1's numbers, not 01-A's).

**WooCommerce behaviour, not verified here:** `orderby=id` for products; `per_page` at most 100 (Known, not re-checked); whether `modified_after` includes its boundary, and its precision; whether a download edit or a meta-only change moves `date_modified_gmt` (SYNC-01's Accept depends on it); whether drafts can have an empty slug.

**Other risks:**
- **Live traffic:** Cloudflare or a WAF may react to bursts (m2.0 R3); the cookie-log follow-up; reads during a change can shift pages (the count check, then one re-read).
- **Size:** the database grows by 30 days of snapshots × 2 stores × 2,402 products, and every daily backup copies it; store only the fetched fields and measure at L2.
- **Process:** 12 §5 assumes no weekly limit for Opus, but the weekly reading is 76 % today, so §5 is revisited with the owner (not decided here); live runs go outside Claude (V36); the M1b exit test is still pending (it doesn't block M3).
