# m2.8: the LocalWP half of the test stack

The test stack is [07 §5](../07-testing.md) and [04 §10](../04-architecture.md) (`testenv/`): a LocalWP site with WooCommerce and the owner's Amazon S3 Storage extension, whose "User defined" endpoint points at moto server (04-A V6–V8). The moto half merged as #43 ([t3-moto-test-server.md](t3-moto-test-server.md), `testenv/moto_s3.py`). This task builds the harness's LocalWP side. The owner approved the plan on 2026-11-03 and installs LocalWP, WooCommerce and the extension themself.

**Transport** (owner, [11](../11-decisions.md) 2026-11-03, m2.0 §3 Q3): the site uses LocalWP's own HTTPS, and only the test harness is given that site's certificate file. The app gains no setting and no package. WooCommerce's REST docs say Basic auth (consumer key as user name, secret as password) is for HTTPS, and plain HTTP needs OAuth 1.0a (developer.woocommerce.com/docs/apis/rest-api/authentication, read 2026-11-03). On this site that is still to prove (§1 "Done", live check).

## 1. Brief

### PRD IDs

### Files (backend, the `builder`)
- **`testenv/localwp.py`** (new): the LocalWP test site's connection, for tests and the seed script only.
  - **Site guard:** the base URL must be `https://<name>.local` (one label of `a-z0-9-` before `.local`, no port, path, user info, query or fragment). Before any key is sent, the host must resolve only to loopback addresses (127.0.0.0/8 or `::1`; LocalWP writes them to the Windows hosts file). Anything else raises, so the harness can never write to a live store.
  - **Certificate:** an `ssl.SSLContext` built from **only** the given certificate file (`cafile=`, no Windows store, no certifi), `CERT_REQUIRED`, hostname checked. It's returned as an `httpx.HTTPTransport(verify=ctx)`, which the read side passes to `WooClient(transport=...)` (the existing seam, `backend/shelfsync/apply/woocommerce.py`). No app code changes. **To verify:** Python 3.14's default contexts set `VERIFY_X509_STRICT`, which may refuse LocalWP's self-signed certificate. If it does, the builder records the exact error and stops at the early check: whether to clear that one flag for this one test context is the analyst's call, recorded in 11.
  - **Keys:** the test site's consumer key and secret live in Windows Credential Manager under a test-only service name (`ShelfSync-testenv-localwp`), via `keyring` (locked). Never in an environment variable, argument, file, URL or log. A small entry point (`uv run python -m testenv.localwp set-keys`) asks for them with hidden input (`getpass`) and prints only a result line (CLAUDE.md rule 7). The **site URL and the certificate path** (not secrets) are passed as arguments or read from `SHELFSYNC_LOCALWP_URL` and `SHELFSYNC_LOCALWP_CA`.
- **`testenv/seed_localwp.py`** (new): fills the test site with sample products shaped like real ones, without customer data or real vendor names.
  - Simple downloadable products and a variable product with downloadable variations. Their download file fields use each form ShelfSync must read (04 §5 `object_ref`): `[amazon_s3 object="<key>"]` (the form on both live stores, 2026-10-25), a direct S3 URL to the moto endpoint, and a URL-encoded key.
  - It puts a matching small sample object for each key into moto (`testenv/moto_s3.py`'s bucket, through ShelfSync's isolated `make_client`).
  - Every product it makes has a SKU starting with `SSTEST-`. A second run changes nothing (idempotent), and `--reset` deletes only `SSTEST-` products (and only their moto objects).
  - **Writes** (POST, PUT, DELETE) go through a testenv-only `httpx.Client` with the same site guard, Basic auth in the header only, `trust_env=False`, no redirects and explicit timeouts. **Never through `WooClient`**, which stays GET-only until M5.
- **`tests/test_testenv_localwp.py`** (new), `httpx.MockTransport` only, in the default suite:
  - the guard refuses http, a non-`.local` host, a port, a path, user info, and a name that resolves to a non-loopback address;
  - the context uses only the given file and checks the hostname;
  - keys never reach a URL, a query string or a log record;
  - the seed payloads have the right shapes;
  - a second run is a no-op, and `--reset` touches only `SSTEST-`.
- **A live check behind a new marker `localwp`**, deselected by default like `windows` (`pyproject.toml` markers and `addopts`), run by the lead once the site exists:
  - `run_read_test` against the site through the certificate transport answers OK;
  - the seed runs, then reads its products back;
  - one probe sends the **test** keys over the site's `http://` address (loopback only) and expects WooCommerce to refuse them. That records the HTTPS-only rule on WooCommerce itself; the analyst may drop the probe at the early check.
  - Without the site, the URL, the certificate or the keys, it **skips with the reason**. It never passes silently.
