### Decisions I took inside the brief (for the lead to record in 11 as Lead (proposed))
1. **`""` is allowed for region and bucket on PUT** (the defaults are empty; a screen must be able to save "not yet"). All five fields are still required in the body.
2. **Endpoint:** `http` or `https` to exactly `127.0.0.1` or `localhost` (any port); otherwise `https` to a dotted DNS name with a letter in its last label (no IP literal, same rule as store addresses); no path except a trailing `/`; scheme in lowercase; at most 200 characters; ASCII only; no userinfo, query, fragment, backslash or space.
3. **Bucket:** the briefed regex plus a refusal of `..` (S3's own rule), in the same check.
4. **Template:** `{key}` exactly once, at most 200 characters, `str.isprintable()` (so no line break, tab or other control character).
5. **Masks differ slightly from m2.1's** (`prefix + •••• + last 4`): a key ID is an identifier, so it shows the **first four** and last four (`AKIA••••ABCD`, always 12 characters); an S3 secret shows a constant **`••••`** (owner's decision D1, 2026-10-28, replacing my first proposal of `•••• + last 4`). Length is never shown.
6. **A failed save puts the earlier pair back** (like m2.1's `StoreCredentials.save`) instead of only deleting what was written, so a failed replacement never loses a working pair. With no earlier pair this is the brief's "leaves nothing".
7. **GET on an unreadable Credential Manager** answers 200 with the masks `null` (as m2.1's stores list does) and logs a warning; only the writes answer 503 `secrets_unavailable`.
8. **One lock** serialises settings saves and key writes in `StorageService`.
9. I did not refactor m2.1's `StoreCredentials` to share code with `S3Credentials`; the pair logic is duplicated (about 40 lines), to keep m2.1's reviewed code untouched.
