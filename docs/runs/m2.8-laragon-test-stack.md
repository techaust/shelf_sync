### What to build
1. **V57 first: the certificate check.**
   - **In tests (CI and this PC):** make a look-alike certificate with `cryptography` (self-signed, `CA:FALSE`, SANs `localhost`, `*.localhost`, `*.test`), serve TLS on 127.0.0.1 port 0, and connect with httpx through an `ssl.SSLContext` built **only** from that certificate file, Python's defaults otherwise (`VERIFY_X509_STRICT` stays on, hostname check on), to the name `shelfsync-test.test` (SNI and hostname check on that name while the socket goes to 127.0.0.1: find the clean httpx/httpcore way and say which). Pin both outcomes: accepted for `shelfsync-test.test`; refused for a name outside the SANs and for a different self-signed certificate.
   - **If Python 3.15 refuses the look-alike** (strict mode or the one-label `*.test` wildcard): **stop and report** with the exact error and the options (for example, a local CA made by the harness and a site certificate signed by it, which means changing Laragon's certificate files, the owner's call). **Never** weaken verification (no `CERT_NONE`, no clearing `VERIFY_X509_STRICT`, no `check_hostname=False`).
   - Update 04-A V57 with what the tests showed (the real Laragon check is the lead's, §6).
2. **`testenv/laragon.py`**, one command with subcommands, run as `UV_PYTHON_DOWNLOADS=never uv run python -m testenv.laragon <command>`:
   - **The site address** is `https://shelfsync-test.test` by default (`--site` to change it). Refuse anything that isn't `https` on a name ending in `.test` (no IP addresses, no other suffix), so a live store address can never be used here. The certificate file defaults to `C:\laragon\etc\ssl\laragon.crt` (`--cert`).
   - **`keys`**: stores the site's two WooCommerce REST key pairs (read-only, and read/write) in Credential Manager under a **separate service name** (propose one, for example `ShelfSync-TestStack`, so ShelfSync's own entries and the uninstaller's "Remove my data" are untouched), via ShelfSync's own `secrets` adapter with that service. Hidden input (`getpass` or a PowerShell `-AsSecureString` prompt), nothing echoed, logged or written to a file; prints one result line per pair ("Saved read-only key pair." or the reason). Key shape checked as Settings › Stores checks it. `keys --remove` deletes exactly these entries.
   - **`check`**: the M2 exit test's store half. Builds ShelfSync's own `WooClient` with `transport=httpx.HTTPTransport(verify=<context from the certificate file>)` and the read-only pair, runs `run_read_test`, and prints the outcome the way Settings words it (13), with the WooCommerce version. Exit 0 only when it passes.
   - **`seed`**: writes the sample products (below) with the read/write pair, through a **testenv-only** client (ShelfSync's `WooClient` stays GET-only: don't change it). Same TLS context, `trust_env=False`, no redirects, keys in the header only. **Idempotent:** each sample has a fixed SKU with a prefix (propose one, for example `ss-test-`); a rerun updates them, never duplicates. `seed --reset` deletes only products with that prefix (force delete), and refuses to touch anything else. Also uploads each sample's small download file to the moto bucket (through ShelfSync's own `make_client`, like T3) so the shortcodes point at real objects, when the moto server is running (`--moto http://127.0.0.1:47630`); without it, says so and still seeds the products.
3. **The sample products**, shaped like the real catalogue (no customer data, no vendor code, made-up names):
   - downloadable simple products, each download's file the shortcode with a made-up key in the real key layout (read 04 §5 and 01's recorded evidence for the layout; don't read the live stores);
   - one product with two downloads; one variable product whose variations carry the downloads (APL-07);
   - one non-downloadable product (V27); one draft, one private and one trashed downloadable product (V1's `status`/`include_status`);
   - two products sharing one key (shared files, 04 `object_ref`).
   Each download file is a tiny ZIP holding only a made-up theme or plugin header (like 07's fixtures). About 12 products in all; say the final list in the report.
4. **Runbook:** write [runbooks/test-stack.md](../runbooks/test-stack.md) §3 click by click for an owner who isn't a shell user (full paths, one command per block):
   - make the site in Laragon named `shelfsync-test` (WordPress from Laragon's own menu; Laragon downloads it), turn SSL on, check `https://shelfsync-test.test` opens;
   - install and activate WooCommerce from wp-admin, set permalinks so `/wp-json/` works, make the two REST keys (Read, and Read/Write), then `keys`;
   - activate the Amazon S3 Storage extension (the owner's own download from their woocommerce.com account) and set its "User defined" provider to the moto server's endpoint, region, bucket and made-up keys (04-A V6, the vendor's documented snippet; quote nothing at length);
   - start moto, then `seed`, then `check`; how to open one sample's download as a logged-in admin to try V6; how to stop and reset.
   Which steps are the owner's and which are Claude's must be obvious. Update `runbooks/README.md`'s row if its wording changes.
5. **Tests** (no Laragon, no network beyond loopback; the conftest `no_outbound_network` guard stays on): V57 as above; `check` and `seed` against a local fake HTTPS WooCommerce (the look-alike certificate, a small fake that answers the REST paths used), including: a non-`.test` or non-`https` site refused before any request; keys never in a URL, a log line or the output; `seed` twice gives the same set; `--reset` deletes only prefixed SKUs; a 3xx isn't followed; a wrong certificate fails as `tls_error`. Credential Manager tests use a fake secrets backend (the real one only under `-m windows`).
