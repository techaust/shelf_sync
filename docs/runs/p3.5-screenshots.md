### Method and fidelity test
- **2× was achieved.** All 30 PNGs come from the capture helper, not from stitching. The 1× fallback was not used.
- **How the helper works** (`capture/capture.js`):
  - It clones the live DOM and copies the form state (checked, value, selected).
  - It inlines every same-origin stylesheet, with `url()` turned into data URLs (Archivo variable, Plex Mono 400 and 500). It also inlines the sprite's `<symbol>`s (rewriting `<use href>` to `#id`) and the logo `<img>`.
  - It copies the `<html>` attributes onto the SVG root, so `:root[data-theme]` rules match.
  - It turns off animations and transitions.
  - It draws an SVG `foreignObject` at a 1440 px layout width and the full height onto a canvas at 2880 px wide (scale 2), then POSTs the PNG.
  - The height is measured with the scrollbar hidden for a moment, so the layout is a clean 1440.
- **The receiver** (`capture/receiver.py`):
  - It binds to 127.0.0.1:8766 only, run as `python -I receiver.py 8766`, with the standard library only.
  - It has one path, `POST /shot?name=`, with names checked against `[a-z0-9-]+\.png`.
  - It checks the size (20 MB cap), the PNG signature and that the origin is `http://127.0.0.1:8765`. It writes atomically through a `.part` file.
- **Fidelity test:** the Dashboard in light, through the helper and as a pane capture, compared side by side at the same scale (`fidelity-side-by-side-dashboard-light.png`), plus a 1:1 crop of the 2× image.
  - **First pass, one mismatch:** inside an SVG image, links don't match `:link`, so the browser's own underline was missing on "View all in Activity" and "Settings". Fixed in the helper with `:where(a[href]){text-decoration:underline}`. It has zero specificity and comes ahead of the page CSS, so every page rule still wins.
  - **Second pass: everything matches.** That covers both fonts (Archivo, including the 116 % width titles, and Plex Mono), all icons, the colours, the logo, the borders and `shadow-1`, the drop zone's diagonal cut, the nav cut, and no focus ring.
- **Two differences are expected, not faults:**
  - The pane lays the page out at 1425 px because of its scrollbar, so two KPI details wrap one word differently.
  - In a full-page image the side nav's footer sits at the foot of the page.
- **Overlay fix:** the first help-panel shot ended short of the bottom. My stand-in for the browser's `:modal` rules outranked the page's `.help-panel { max-height: none }`. I moved those rules to zero specificity ahead of the page CSS and retook the shot; the panel now runs the full height.
- I compared the ConfirmDialog shot against a pane capture of the same open dialog, and it matches.
