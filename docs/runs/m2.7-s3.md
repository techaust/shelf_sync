### The 3-step Test, exactly
`POST /api/storage/test`: no body, behind the guard (session, Origin, `X-ShelfSync: 1`), a sync handler like `POST /api/stores/{id}/test`.

**Before any request:**
1. Claim a non-blocking busy flag, or answer 409 `busy`.
2. Under `StorageService.lock`, snapshot the three settings and the four key values, then release it. **Never hold `SECRETS_WRITE_LOCK` across network I/O.**
3. Read the settings strictly: an empty or invalid `s3_region` or `s3_bucket`, or an invalid `s3_endpoint` → 409 `storage_not_set` (re-check with `check_s3_endpoint`, `check_s3_region`, `check_s3_bucket` from `db/settings.py`).
4. Read the keys with `S3Credentials.read()`, not `pair()` (which turns a Credential Manager failure into None): `SecretStoreError` → 503 `secrets_unavailable`; a missing value in either pair → 409 `keys_missing`. Register all four values with `redact`.

**Test object (Lead (proposed)):** key `shelfsync-test/<YYYYMMDDTHHMMSSZ>-<secrets.token_hex(16)>.txt`; body `b"ShelfSync storage test " + nonce + b"\n"`; `ContentType="text/plain; charset=utf-8"` and `ContentMD5` (base64), the path APL-02's uploads will use; no ACL, no metadata, no `IfNoneMatch`.

| Step | Key pair | Requests | Passes when |
|---|---|---|---|
| 1 write | `rw` | `put_object` (one request; never `upload_file` or multipart) | 2xx |
| 2 read | `ro` | `get_object` on the same key; read at most `len(body)+1` bytes; close the body in `finally` | the bytes equal what was written |
| 3 delete | `rw` | `delete_object` on exactly the key step 1 wrote, then `head_object` on it | DELETE 2xx, then HEAD 404 |

- A failed write: steps 2 and 3 are `not_run` (mockup `screens-b.js:553-562`).
- **A passed write is always followed by the delete, even if the read failed** (L2).
- HEAD 403 fails step 3 with `confirm_forbidden`; HEAD 200 with `still_there`.
- `apply/s3.py` has **no public put or delete that takes a caller's key** in m2.7: the delete exists only inside the Test, on the key the Test generated.

**Time limits (L7, Lead (proposed)):** per request connect 5 s, read 10 s; retries `{"mode": "standard", "total_max_attempts": 2}`; the whole Test 30 s plus 5 s grace, with the store test's worker-thread and deadline pattern (`store_service.py:410-494`, including the overrun hand-off of the busy flag). On overrun the running step is `failed`/`timeout` and later steps `not_run`; the worker skips the read but still deletes if the write succeeded, and logs the outcome; the busy flag is held until the worker ends.

**Response (200 even on failure, like the store test):**
```json
{"ok": false, "tested_at": "2026-11-02T10:00:00Z", "latency_ms": 412,
 "steps": [
  {"step": "write",  "key_pair": "rw", "state": "passed", "latency_ms": 180, "reason": null, "aws_code": null, "http_status": null},
  {"step": "read",   "key_pair": "ro", "state": "failed", "latency_ms": 95,  "reason": "access_denied", "aws_code": "AccessDenied", "http_status": 403},
  {"step": "delete", "key_pair": "rw", "state": "passed", "latency_ms": 137, "reason": null, "aws_code": null, "http_status": null}],
 "left_behind": null}
```
- `state`: `passed | failed | not_run`. `left_behind`: the test key when step 1 passed and step 3 didn't; otherwise null.
- `aws_code`: the S3 error `Code` only, kept only if it matches `^[A-Za-z0-9.]{1,64}$`. **Never the `Message`** (it can hold the account ID and ARNs) and nothing else from `e.response` (L4).
- No endpoint, bucket, key ID or secret in any response. Errors use the fixed bodies: 409 `busy`, `storage_not_set`, `keys_missing`; 503 `secrets_unavailable`.

**`reason`** (a `Literal` in `apply/s3.py`, mapped by a pure `classify(exc)`):

| Reason | When |
|---|---|
| `access_denied` | `AccessDenied`, `AllAccessDisabled` |
| `key_unknown` | `InvalidAccessKeyId` |
| `secret_wrong` | `SignatureDoesNotMatch` |
| `clock_wrong` | `RequestTimeTooSkewed` |
| `bucket_missing` | `NoSuchBucket` (ERR-03) |
| `wrong_region` | `AuthorizationHeaderMalformed`, `PermanentRedirect` or `IllegalLocationConstraintException` that survived botocore's redirector |
| `not_found` | read: `NoSuchKey` or 404 |
| `mismatch` | read: bytes differ |
| `confirm_forbidden` | the delete step's HEAD answered 403 |
| `still_there` | the delete step's HEAD answered 200 |
| `refused` | any other 4xx with a code |
| `server_error` | 5xx after retries, `SlowDown` |
| `unreachable` | `EndpointConnectionError`, `ConnectionClosedError` |
| `timeout` | `ConnectTimeoutError`, `ReadTimeoutError`, the deadline |
| `tls_error` | `SSLError` |
| `bad_response` | a parser error or anything unexpected |

Logs: one INFO line per Test (step, reason, `aws_code`, status, ms), never `str(exc)` (`EndpointConnectionError` text holds the URL), and no endpoint, bucket or object key (the rule at `store_service.py:13`).

### The S3 client (`apply/s3.py`)
- **One client per key pair per Test**: `rw` and `ro` built from one snapshot and `close()`d after. A fresh botocore Session per build (Sessions aren't thread-safe; clients are). M5 may add a cache.
- **Isolation (L9):** `botocore.session.Session(session_vars={"profile": (None, None, None, None), "config_file": (None, None, <a path that never exists>, None), "credentials_file": (same)})` (`session.py:158-160, 1255-1277`; `configprovider.py:71-80`; its effect proven by the test below); explicit credentials, `region_name`, `verify=True`; `endpoint_url` = the setting, or None for AWS.
- **`Config`**, every value explicit:

  | Option | Value |
  |---|---|
  | `connect_timeout`, `read_timeout` | 5, 10 |
  | `retries` | `{"mode": "standard", "total_max_attempts": 2}` |
  | `proxies` | `{}` (no proxy, like the stores' `trust_env=False`) |
  | `ignore_configured_endpoint_urls` | True |
  | `use_fips_endpoint`, `use_dualstack_endpoint` | False |
  | `defaults_mode` | `"legacy"` |
  | `signature_version` | `"s3v4"` |
  | `request_checksum_calculation`, `response_checksum_validation` | `"when_required"` for a non-AWS endpoint (V10); `"when_supported"` for AWS (L5) |
  | `s3.addressing_style` | `"path"` for a custom endpoint; `"auto"` for AWS (L6; record what botocore does with a dotted bucket name) |

- **Lazy import (L10):** `boto3`/`botocore` imported inside the factory, types under `TYPE_CHECKING`, so start-up doesn't load botocore (NFR-3).

- **Logging:** `logs.py:193` holds `httpx` and `httpcore` at WARNING; add `botocore`, `boto3`, `s3transfer` and `urllib3` (at DEBUG botocore logs headers).
- **Never:** presigned URLs, `upload_file`, the region redirector's cache across Tests.

### Decisions in this brief (11, Lead (proposed))
L1 the Test's own write and delete run inside the request (bounded, one at a time, only its `shelfsync-test/` object), an exception to 04 §5 noted there; L2 the delete always follows a successful write; L3 the delete step confirms with a HEAD expecting 404; L4 the AWS error Code only, never the Message; L5 checksum settings by endpoint kind, `ContentMD5` on the test write; L6 path style for custom endpoints; L7 the time limits; L8 no persisted S3 health in m2.7; L9 client isolation from the environment and `~/.aws`, no proxy; L10 boto3 imported lazily; L11 strict settings read for the Test; L12 one new error code; L13 (early check C4) a failed write that may have reached S3 (`ReadTimeoutError`, `ConnectionClosedError`, `ResponseStreamingError`, or a 5xx other than `SlowDown`) is cleaned up with the same DELETE + HEAD, steps 2 and 3 staying `not_run`, and `left_behind` names the key unless the HEAD confirmed a 404.

### Costs to flag (rule 6)
Each click makes 4 requests (a tiny AWS charge); a write that fails in a way that may still have reached S3 (L13) is followed by the clean-up's DELETE and HEAD: two more requests than a write that simply failed. A retried 5xx or lost answer adds one request each (two attempts at most per request). If bucket versioning is on (still unrecorded, 06 §9), each Test leaves a tiny old version and a delete marker, since the read-and-write policy has no `s3:DeleteObjectVersion` (not added: it would widen the key).

**Choices beyond the brief's text (please check):**
1. **`~/.aws/models` and `AWS_DATA_PATH`:** botocore loads service models from both, so a file there can replace S3's model. `make_client` registers a `Loader` with only botocore's own data folder (and `data_path` is in `session_vars`). The control test shows the planted model does break a plain client.
2. **botocore swallows the conftest network guard:** `OutboundNetworkBlocked` raised in a socket becomes `HTTPClientError` (→ `unreachable`), so an outbound attempt could pass a test. `tests/s3_support.py::s3_guard` (autouse in every S3 test module) records each blocked attempt and fails the test; it also records every S3 operation and fails if anything but a `shelfsync-test/<pattern>` key is ever PUT or DELETEd.
3. **moto in-process doesn't intercept a custom endpoint** (only AWS host patterns), so custom-endpoint tests use `FakeS3` (before-send, no socket) or 127.0.0.1 servers; the `ThreadedMotoServer` (V8) tests come in stage 2.
4. **`classify` extras:** the `HTTPClientError` family (incl. `ProxyConnectionError`, `ResponseStreamingError`) → `unreachable`; `FlexibleChecksumError` → `mismatch`; a Code that is only the HTTP status (botocore's stand-in for a body-less HEAD answer) is dropped (`aws_code: null`); a 404 without a Code → `not_found`; 3xx without a known Code → `bad_response`.
5. **The worker logs** the one INFO line (`run_storage_test` doesn't), so a late result is logged with "(finished after the answer was sent)".
6. **A client that can't be built** is a 500 `internal` (a bug, not a storage answer); the busy flag is freed.
