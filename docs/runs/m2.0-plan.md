### m2.2-db-backups [BAK-01, part of SET-05] · Tier B
`builder` Sonnet medium.
- **Files:** `db/daily.py`, `db/restore.py` (a command), `db/settings.py`, `api/backup_settings.py`, the lifespan in `api/app.py` (start and stop the scheduler like `UpdateService`).
- **Settings:** `db_backups_kept` (7, 1–30); `snapshot_retention_days` (30, 1–365; only stored now, used in M3).
- **Schedule** (Lead (proposed)): due at **02:00 Windows local time** (the mockup's "The first runs tonight at 02:00"). A missed run is caught up at the next start or wake. The loop checks the wall clock every 60 s, so a sleep is noticed. Local time from `datetime.astimezone()` (`tzdata` isn't locked). The last backup time comes from the newest file name, so nothing is stored.
- **Format:** `backups\daily-YYYYMMDDTHHMMSSZ.db`: an online backup on the scheduler's own connection into `….db.part`, then `PRAGMA journal_mode=DELETE` and `integrity_check`, then `os.replace`. Stray `daily-*.db.part` files are removed at start through `paths.remove_entry`. Reuse `_write_checked_copy`.
- **Retention (the rule that protects kept versions):** deletes **only** plain files (links never followed) named `^daily-\d{8}T\d{6}Z\.db$`, sorted by the time in the name, keeping the newest `db_backups_kept`. It runs only after a new backup passed its check. `pre-migration-*`, `pre-rollback-*` and the files `update\state.json` names (also checked by resolved path) are never touched. Lead (proposed): no automatic pruning of pre-migration or pre-rollback copies in M2. Lowering the setting prunes at once.
- **API:** `GET /api/settings/backup` → `{db_backups_kept, snapshot_retention_days, last_backup_at, last_backup_bytes, next_backup_at, daily_count}`; `PUT` takes the two settings.
- **Restore command** (`restore-database.md`): `python -m shelfsync.db.restore [--list | <file name>]`. Refuses while ShelfSync runs (`default_instance_lock`), takes a `take_snapshot` copy first, accepts only `daily-`, `pre-migration-` and `pre-rollback-` files inside `backups\`, refuses a schema newer than this app knows, reuses `restore_backup` (its allowed prefixes gain `daily-`).
- **Tests:** a fake clock over 8 days leaves 7 files (BAK-01's Accept test); a restored daily copy passes `check_backup`; a failed backup prunes nothing; planted `pre-migration-*`, `pre-rollback-*`, `state.json`-named files, a link and a foreign name all survive; catch-up after a missed 02:00; a DST change (fake offset); a `.part` cleaned at start; the scheduler stops cleanly (bounded wait).

### m2.4-backup-export [SET-05] · Tier A
`builder` Sonnet high, after m2.1–m2.3. Context7 for `AESGCM`.
- **Files:** `secure/backup_crypto.py` (pure seal and open), `db/export.py`, `api/backup.py`.
- **KDF (decided):** `hashlib.scrypt(NFC(passphrase).encode(), salt=16 random bytes, n=2**17, r=8, p=1, maxmem=256*1024*1024, dklen=32)`.
- **Cipher (decided):** `AESGCM(key).encrypt(12-byte random nonce, data, aad)` (the tag is appended: to verify with Context7). New salt and nonce every export.
- **Passphrase** (Lead (proposed)): 12–1024 characters, NFC-normalised, never logged, registered with `redact`.
- **File `.ssbak`** (Lead (proposed)), UTF-8 JSON: `{"format":"shelfsync-export","version":1,"created_at","app_version","schema","encryption": null | {"cipher":"AES-256-GCM","kdf":"scrypt","n":131072,"r":8,"p":1,"salt","nonce"}, "payload"` (unencrypted only) `, "sha256"` (unencrypted only: corruption check, not authenticity) `, "ciphertext"` (encrypted only) `}`.
  - **AAD** = the canonical JSON (`sort_keys`, `separators=(",",":")`, `ensure_ascii`) of every header field except `ciphertext`, so a downgrade or a cost change fails the tag.
  - Import accepts only `n=131072, r=8, p=1` for version 1; costs are never taken from the file.
  - **Payload v1:** `settings`, `stores` (keyed by `code`), `storage`, `catalog: null`, and `secrets` (store keys by code, the four S3 values, the GitHub token) **only in encrypted files**. The install token is never exported. M3 adds the catalog as version 2.
- **API:** `POST /api/backup/export` `{passphrase|null}` → 200 JSON with `Content-Disposition: attachment; filename="shelfsync-export-<local date>.ssbak"`; 409 `busy` (one KDF at a time). `POST /api/backup/import` `{file (≤ 32 MiB), passphrase|null}` → 200 counts; 422 `export_invalid`, `passphrase_required`, `wrong_passphrase`; 409 `export_too_new`, `import_needs_empty`, `busy`; 503 `secrets_unavailable`.
- **Import order:** size cap → parse → header check (format, version, exact KDF parameters) → decrypt and check the tag (or the SHA-256) → validate the whole payload with the API's Pydantic models → **only then** one transaction, with the Credential Manager writes before the commit; on a failure roll back and delete the entries written.
- **Import rule** (Lead (proposed)): only into an install with no stores (a fresh install or a new PC); otherwise 409 `import_needs_empty`.
- **Tests (07 §1 "Backup"):** round trip with and without a passphrase (the real scrypt parameters at least once); a wrong passphrase changes nothing; tampered ciphertext, header, AAD or KDF parameters fail; raised KDF costs refused before any derivation; a plain file holding `secrets` refused; oversize, unknown version and newer schema refused; the install token never exported; the passphrase never logged; a failure halfway leaves no row and no entry.

## 2. The two IAM policies (06 §5; `BUCKET` filled in on screen)
Read and write (daily use):
```json
{"Version":"2012-10-17","Statement":[
 {"Sid":"ShelfSyncObjects","Effect":"Allow","Action":["s3:GetObject","s3:PutObject","s3:DeleteObject"],"Resource":"arn:aws:s3:::BUCKET/*"},
 {"Sid":"ShelfSyncList","Effect":"Allow","Action":"s3:ListBucket","Resource":"arn:aws:s3:::BUCKET"}]}
```
Read-only (calibration, teach, the read step of the Storage test):
```json
{"Version":"2012-10-17","Statement":[
 {"Sid":"ShelfSyncRead","Effect":"Allow","Action":"s3:GetObject","Resource":"arn:aws:s3:::BUCKET/*"},
 {"Sid":"ShelfSyncList","Effect":"Allow","Action":"s3:ListBucket","Resource":"arn:aws:s3:::BUCKET"}]}
```
To add to 04-A (to verify against the AWS docs): `s3:GetObject` covers HEAD and range GETs; with `s3:ListBucket` a missing key answers 404, not 403 (APL-08 and APL-14 rely on it); SSE-KMS with its own key needs `kms:Decrypt` and `kms:GenerateDataKey`; the read-and-write key could delete objects ShelfSync didn't upload (the code never does, APL-07): a residual risk for 06 §10.
