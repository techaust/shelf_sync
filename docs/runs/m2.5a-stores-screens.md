### What to build
1. **Settings › Stores** (replaces the "later version" panel), on `GET /api/stores`, `POST /api/stores`, `PATCH /api/stores/{id}`, `PUT /api/stores/{id}/keys`, `DELETE /api/stores/{id}` and `POST /api/stores/{id}/test`:
   - **One card per store**, as the mockup has it: name, address, the identifier (shape, colour key, two-letter code) with a live StoreBadge preview, "Time between requests" in seconds (shown with up to two decimals, sent as `spacing_ms`, 0.05–5 s), the main-button choice, and the state (live or paused).
   - **Keys:** the consumer key and secret as one SecretField pair. The API returns masks only: show the mask, "Not set", or, when `keys_readable` is false, "Couldn't be read" (never "Not set" then). A new pair is always sent as a pair and the inputs are cleared after a save.
   - **Address change:** when the address's host changes, the API answers `keys_required` unless new keys come in the same request. The card asks for them together, with the 13 text.
   - **Test connection:** shows the 13 result ("Connected in N ms. WooCommerce X, N downloadable products.") or the reason, with `tested_at` in Windows local time with the zone name. While it runs, the button shows progress and a second click does nothing; `busy` uses its 13 text.
   - **Pause / Resume** per store; **Remove** behind a ConfirmDialog (destructive) that says the keys are deleted at once.
   - **Add a store:** an empty card. When 50 live stores exist the API answers `too_many_stores`; show its 13 text.
   - **Identifier picker:** the shapes the API accepts and the colour keys in `storePalette.ts`. A code another store uses is refused by the API (`code_taken`); show it at the field. **Don't add colour pairs.** If you think more are needed, propose up to four in the report, each with its 3:1 contrast result on every surface, for the owner's approval.
   - Every API error code is shown with its 13 wording, at the field it belongs to where there is one.
2. **The HealthArea** in the shell, from `GET /api/stores` (refreshed after each test, save or remove, and when the window regains focus; no timer polling):
   - one chip per live store, with its StoreBadge;
   - a healthy chip is a read-out; a store whose last test failed is a button that opens the reason, `tested_at` and one "Test connection" action (ERR-01), as the mockup's popover has it;
   - a store never tested says so and offers the test;
   - paused stores show as paused, never as failed.
3. **The Help panel** (UI-HELP, guides only), opened from each screen's header as in the mockup, with a native `<dialog>` like ConfirmDialog (Esc closes it, and the focus returns to the opener):
   - **Make a Shop Manager key**, from the runbook §A.
   - **Set up the S3 access policy (IAM)**: both policies from m2.0 §2. The bucket name comes from `GET /api/settings/storage`: when it is empty, show `BUCKET` and a line saying to fill in the bucket under Settings › Storage first. Each policy has a Copy button. If `navigator.clipboard` isn't available on `http://127.0.0.1`, select the text and say "Press Ctrl+C to copy" instead. Check which happens in the pane and report it.
   - **Make a GitHub token for updates**: a fine-grained, read-only token for this one repository. Keep it in line with what Settings › Updates already says about the token (13 §3 and the 11 rows of 2026-10-27).
   - The panel holds no glossary yet. Leave a clear place for M5's per-screen help and "What does this word mean?".
   - Propose the guide texts in the report, in 13's plain style.
4. **The API client:** use the generated types and `client.ts`'s typed calls and error codes. Every write sends what the guard needs (the client does already).

### Done means
- In `frontend/`, all pass:
  - `npm run lint`, `npm run typecheck`, `npm run build` and `npm run schema:check`;
  - `npm test` (Vitest), covering each card state (no keys, keys saved, keys unreadable, tested OK, test failed, paused), the address-change rule, the spacing conversion and its limits, the Remove dialog's keyboard behaviour, every error code's text, the HealthArea states, the Help panel's focus handling and the Copy fallback.
- The Python checks still pass (`uv run pytest`).
- **Screenshots** in the built-in browser pane, light and dark, at 1280 px wide, of:
  - Stores with two stores (one healthy, one failed);
  - a card with unreadable keys;
  - the Add card with a field error;
  - the Remove dialog;
  - the HealthArea popover;
  - the S3 guide with and without a bucket.

  Use the dev server with mocked API answers, or the real server with a throwaway `SHELFSYNC_DATA_DIR`; nothing ever talks to a real store.
- axe-style checks by hand: labels, focus order, contrast from the tokens (the contrast test).
- The designer report (§3) lists:
  - files, commands and results;
  - what wasn't verified;
  - the 13 wording for every new string;
  - the clipboard result in the pane.
