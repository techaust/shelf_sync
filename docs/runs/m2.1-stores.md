### What to build
1. **Migration `db/migrations/0002_store.sql`** (amends 04 §4):
   ```sql
   CREATE TABLE store (
     id INTEGER PRIMARY KEY AUTOINCREMENT,          -- ids never reused (secret names use them)
     name TEXT NOT NULL CHECK (length(name) BETWEEN 1 AND 60),
     url TEXT NOT NULL,                             -- normalised https://host[:port][/path], no trailing /
     code TEXT NOT NULL CHECK (code GLOB '[A-Z][A-Z]'),
     shape TEXT NOT NULL CHECK (shape IN ('circle','square','triangle','diamond')),
     color TEXT NOT NULL,                           -- a palette key, not a hex
     spacing_ms INTEGER NOT NULL DEFAULT 150 CHECK (spacing_ms BETWEEN 50 AND 5000),
     main_button TEXT NOT NULL DEFAULT 'Download' CHECK (length(main_button) BETWEEN 1 AND 40),
     state TEXT NOT NULL DEFAULT 'active' CHECK (state IN ('active','paused')),
     wc_version TEXT, wp_version TEXT,
     health TEXT NOT NULL DEFAULT 'unknown' CHECK (health IN ('unknown','connected','unreachable','refused')),
     health_reason TEXT, http_status INTEGER, latency_ms INTEGER, downloadable_count INTEGER, tested_at TEXT,
     created_at TEXT NOT NULL, removed_at TEXT      -- soft delete (history from M3 points at store ids)
   );
   CREATE UNIQUE INDEX store_url_live  ON store(url)  WHERE removed_at IS NULL;
   CREATE UNIQUE INDEX store_code_live ON store(code) WHERE removed_at IS NULL;
   ```
   Check how migrations are numbered, applied and listed (and whether `schema_version` or a manifest test counts them), and follow it. A test applies 0002 to a 0001 database with `setting` rows; they survive, and `migrate_with_backup` takes the pre-migration backup.
2. **The colour palette:** `color` is a key from a fixed palette of store identifier colours. Find where store colours live today (05 §2.3, `brand/tokens.json`, `frontend/src/components/StoreBadge.tsx`) and reuse those keys. Don't invent hex values. If there's no list of keys, stop and report what you found.
3. **`db/stores.py`:** the repository (list live stores, get, insert, update, soft delete, save a test result).
4. **`secure/credentials.py`:** entry names `store-<id>-key` and `store-<id>-secret` under the existing service (reuse the M1a.2 secrets adapter in `platform/secrets.py`); masking as `prefix + "••••" + last 4` (never the length); registration with `redact.register_secret` when a value is set **and** at start-up (`server.py` reads every stored store secret and registers it; if that read fails, log a WARNING and start anyway, and the test then answers `keys_missing`).
5. **`apply/woocommerce.py`: the read client, GET only.**
   - HTTP Basic over HTTPS only; **never** `consumer_key=` in a query string.
   - `follow_redirects=False`: a 3xx gives `redirected`, naming the target host; the keys never go there.
   - Responses streamed and capped at 1 MiB. Timeouts: connect 10 s, read 30 s, 60 s for the whole test.
   - `User-Agent: ShelfSync/<version>`.
   - The class has **no method other than GET** until M5, and its transport wrapper refuses any non-GET. A contract test proves it.
   - Logs name a store by its code, never its URL, and hold only the reason code and status, never a body.
6. **The read test** (two GETs, `spacing_ms` apart):
   1. `GET {url}/wp-json/wc/v3/system_status?_fields=environment` → `environment.version` (WooCommerce) and `environment.wp_version`. Below 5.8 → `wc_too_old`.
   2. Wait `spacing_ms`.
   3. `GET {url}/wp-json/wc/v3/products?downloadable=true&status=any&per_page=1&_fields=id` → the `X-WP-Total` header is the downloadable count; its round trip is the latency. A count of 0 is `ok` with a warning.
   4. Reasons (and the health state each shows): `unreachable` (DNS or connect), `timeout`, `tls_error`, `redirected` (names the host), `blocked` (403 or 503 HTML: a firewall or Cloudflare challenge), `not_woocommerce` (404, `rest_no_route`, or a 200 that isn't JSON), `rate_limited` (429), `cloudflare_52x` (520–527), `server_error` (other 5xx), `bad_response` (missing fields or no `X-WP-Total`) all show **unreachable**; `keys_refused` (401), `forbidden` (403 with WooCommerce JSON) and `wc_too_old` show **refused**.
   5. The result is saved on the store row. No retries (APL-12 is M3).
7. **`api/stores.py`** (behind the existing guard; the route-walk test must cover every route):
   - `GET /api/stores` → `{stores: [Store]}`, `Store` = `{id, name, url, code, shape, color, spacing_ms, main_button, state, keys: {consumer_key: masked|null, consumer_secret: masked|null}, health: {state, reason, http_status, latency_ms, wc_version, wp_version, downloadable_count, tested_at}}`. `health.state` uses the frontend's `ConnectionState` plus `unknown` (add it in `api/placeholder.ts`).
   - `POST /api/stores` `{name, url, code, shape, color, spacing_ms?, main_button?, consumer_key, consumer_secret}` → 201 `Store`; 422 `invalid_request`; 409 `store_exists` (same live URL), 409 `code_taken`; 503 `secrets_unavailable`.
   - `PATCH /api/stores/{id}` any subset of `{name, url, code, shape, color, spacing_ms, main_button, state}`. A URL change resets the health to `unknown`. **A host change must come with new keys in the same request** (`consumer_key`, `consumer_secret`), or 422 `keys_required`. 404 `not_found`.
   - `PUT /api/stores/{id}/keys` `{consumer_key, consumer_secret}` (always a pair) → 204; the health resets.
   - `DELETE /api/stores/{id}`: deletes both Credential Manager entries **first**; if that fails, 503 and nothing changes; then sets `removed_at`. 204.
   - `POST /api/stores/{id}/test` → 200 `{ok, state, reason, http_status, latency_ms, wc_version, wp_version, downloadable_count, tested_at}` (a failed test is still a 200 with `ok: false`); 409 `busy` (one test per store at a time), 409 `keys_missing`, 404 `not_found`. A paused store can be tested. It runs inside the request (04 §5 forbids only writes there).
   - **Validation** (Lead (proposed)): `consumer_key` `^ck_[A-Za-z0-9]{20,64}$`, `consumer_secret` `^cs_[A-Za-z0-9]{20,64}$` (loose, matching `redact`'s pattern; WooCommerce's exact format is to verify). URL: `https` only, an ASCII host name (no IP literal), no userinfo, query or fragment, at most 200 characters, scheme and host lowercased, no trailing `/`. Unknown fields refused.
   - **Saving is atomic:** insert the row in an open transaction, write both entries, then commit; on a failure roll back and delete any entry already written.
8. **"Remove my data"** (`uninstall.py`, `platform/secrets.py`): also delete `store-<id>-key` and `store-<id>-secret` for every `store.id` (removed rows too), reading the database read-only. If it can't be read, use the existing exit 5 or 6 wording. Add the four S3 names (`s3-rw-key-id`, `s3-rw-secret`, `s3-ro-key-id`, `s3-ro-secret`) to `OWNED_SECRET_NAMES` now, so m2.3 doesn't touch the uninstall path.
9. **Strings:** list every new owner-facing string (each reason, each error code) with proposed 13 wording in the report. The mockup has "HTTP 401: the Shop Manager key was refused." and "Connected in N ms. WooCommerce X, N downloadable products."

### Tests
- Fakes through `httpx.MockTransport`, built from the WooCommerce docs. Hosts from RFC 2606 only (`store-a.example`), never real addresses: the repo is public.
- Every reason above. Exactly two GETs per test, `spacing_ms` apart (fake clock), each with `Authorization: Basic`, and no secret in any URL. The redirect isn't followed. The 1 MiB cap. Non-GET refused.
- Every field's limits; unknown fields; `keys_required`; atomic save (a fake secret store that fails on the second `set`) and delete; the masks.
- With known secret values set, every GET route's body is scanned and must not contain them; every secret through every log path (extend `test_never_logged.py`).
- The uninstall list includes the store entries; the S3 names are in `OWNED_SECRET_NAMES`.
- The guard cases and the route walk.
- A `-m windows` test: six entries under a throwaway service, set, get, replace and delete each, nothing left.
