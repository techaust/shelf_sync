# m3.2: incremental sync and the nightly snapshot

The second M3 task ([m3.0](m3.0-plan.md) §1). m3.1 reads every store in full and builds the catalog ([m3.1](m3.1-catalog-read.md)); m3.2 keeps it current: a small incremental read every 15 minutes, and a nightly snapshot at 02:00 that also finds products trashed or deleted outside ShelfSync. L1 is complete ([t9 §7](t9-l1-diagnostics.md)): both stores read in full (2,398 products each, about 2.5 s a page, pages up to 345 KB); PluginWay stalled for minutes twice on an evening (about 21:45–22:50 IST) and read cleanly the next morning, so **a store that stalls at night must not cost the night's snapshot**.

### How it works
- **Settings (item 1):** `sync_interval_minutes` (int 5–240, default 15) and `snapshot_time` (`HH:MM`, 00:00–23:59, default `02:00`) in `db/settings.py` with the same rules at the API. `GET /api/settings/app` shows them; the scheduler reads them at each check, so a change applies within a minute.
- **Migration 0004 (item 2):** `sync_state` gains `watermark_gmt` (CHECKed to the store's `YYYY-MM-DDTHH:MM:SS`) and `inc_started_at`, `inc_finished_at`, `inc_reason`, `inc_http_status`, `inc_rows`, `inc_changed`, `inc_last_ok_at`. A store whose full read worked under 0003 gets `watermark_gmt = max(modified_gmt)` of its saved rows. `snapshot_night` (store, night, state `running|ok|retry|failed|skipped`, attempts 0–3, started, finished, `next_try_at`, reason, HTTP status, listing `include_status|two_listings`, products, trashed, not_seen, variable) and `snapshot_state` as the brief proposed, plus `variations_json` (each variation's id, status, downloads and `latest_version*` meta; `[]` for other products; at most 4 MiB). Indexes: `(store_id, wc_id, last_night)` and `(last_night)`.
- **The incremental (item 3):** `system_status`, then `GET /products?modified_after=<watermark − 2 min>&dates_are_gmt=true&status=any&orderby=id&order=asc&per_page=100&page=n&_fields=<the full read's>` with m3.1's session (spacing, APL-12 retries and failure count, the 10-minute bound, the stop), the count check, the page and listing caps and the hostile-answer checks; no row is a result, not `no_products`. A store with no watermark is skipped (`no_full_read`). Saved in one transaction (`save_incremental` → `apply_products`): existing rows get the new slug, title, type, status, date, downloads and meta (written only when something differs, so a repeat changes nothing, `seen_at` included); one with no downloads now is kept with them emptied and stays present; a new product with downloads (not in the trash) is linked with m3.1's `plan_links`; any other new one is ignored; the touched items' titles and slots are planned again. The watermark becomes the largest of itself and the returned rows' `date_modified_gmt`, only after a read that fully worked.
- **The snapshot (item 4):** `system_status`; a one-row probe `include_status=trash&per_page=1`; then `include_status=any,trash` with `_fields=id,slug,status,type,date_modified_gmt,downloads,meta_data`. The one listing is kept only when its trashed rows equal the probe's `X-WP-Total`; otherwise, or when the store answers `rest_invalid_param` (a 400 that isn't counted as a failure), it falls back to `status=any` then `status=trash` (`listing` says which). A store that refuses or ignores `status=trash` fails the night with `trash_unlisted` (without a trash listing every trashed product would read as deleted). An empty store fails with `no_products` (same reason). Then each variable product's `/products/{id}/variations` (`_fields=id,status,date_modified_gmt,downloads,meta_data`, at most 4 pages); more than 50 variable products stop that store's night (`too_many_variable`) before any variation request. Saved in one transaction (`db/snapshots.save_snapshot`): the catalog part (`apply_products` in snapshot mode), the state rows, the night (`ok` and its counts), and retention.
- **The scheduler (item 5):** `catalog/scheduler.py`, one thread started by the sync router's lifespan for the app's service only (`build_catalog_service(..., scheduled=True)`; `create_app`'s default in-memory service and every test service never start it). Every 60 s, when no run is going: the snapshot of the current night for the stores it is due on, else an incremental when one interval has passed since the last incremental started (Sync now's included) or since the scheduler started, and some active store has a watermark and isn't auto-paused. The night is the local date of the latest `snapshot_time` (the `db/daily.py` `LocalTime` pattern), so a PC off or asleep catches up at the next check, and a sleep across several nights catches up the latest night only. Every run goes through m3.1's runner (one at a time, busy slots, address guard); a run that is due while another runs waits for the next check after it ends; `POST /api/sync` answers `sync_running` while a scheduled run goes.
- **Sync now (item 5):** `POST /api/sync` takes an optional body `{kind: "full" | "incremental" | null}`; without a kind it is an incremental once every active store has `last_ok_at` and a watermark (`choose_kind`), else a full read. The wizard's Build catalog should send `full` (the screen is m3.4; today's screen sends no body, which still gives a full read while no catalog exists). `kind: "snapshot"` is a 422: the snapshot is the scheduler's.
- **`GET /api/sync` (item 5):** adds the run's `kind` and `night`, and per store `incremental` (started, finished, last ok, reason, HTTP status, rows, changed), `snapshot` (the latest night's row), `next_incremental_at` (null when the store can't have one) and `next_snapshot_at` (now when due, the retry time when waiting, else the next snapshot time). UTC ISO times; nights are local dates.
- **Change detection (item 6):** `catalog/changes.py`: `ProductState`, `Change(store_id, wc_id, kind, fields, before, after, source)`, `compare`, `detect`, `counts`; `kind` is `changed` (downloads, slug, status or type differ; `fields` says which), `trashed` (now in the trash, wasn't), or `deleted` (missing from a snapshot's listing). `apply_products` returns them; the runner logs counts only and hands them to `on_changes` (a `CatalogService` keyword; m3.3 plugs Cleanup in there).
- **`GET /api/catalog/{id}/snapshots` (item 7):** `{item_id, stores: [{store_id, wc_id, nights: ["YYYY-MM-DD", …]}]}`, newest first, one entry per store product of the item on stores that aren't removed; 404 `not_found` as `GET /api/catalog/{id}`.

### Lead (proposed) choices made here (each needs a row in 11 at m3.6)
1. **The auto-pause rule for snapshot attempts** (`catalog/schedule.py`, `runner._NightFailures`, `db.catalog.record_failure_capped`):
   1. a snapshot attempt's failed requests count toward APL-12's ten like any read's, but **never past nine**, so a snapshot attempt never auto-pauses a store by itself;
   2. while a store's night waits for its retry, its **scheduled** incrementals are skipped (`snapshot_retry`; Sync now still reads it);
   3. so a store slow through the night's attempts isn't paused, and its count goes back to 0 at its first usable page; a store still failing after the night's last attempt sits at nine, and its next failed request (the next scheduled incremental's first) pauses it, about 15 minutes after the last attempt.
   Tested: down all night → 4, 8, 9 after the three attempts, not paused, paused by the next incremental; already at 6 before the night → 9, then 0 after a good third attempt.
2. **The same-night retry:** 30 minutes after a failed attempt, at most 3 attempts a night (the brief's numbers), except for reasons waiting can't change (`paused`, `auto_paused`, `store_removed`, `address_changed`, `keys_missing`, `keys_refused`, `forbidden`, `wc_too_old`, `too_many_pages`, `too_many_variable`, `trash_unlisted`, `snapshot_too_large`, `no_catalog`) or an auto-paused store. An attempt stopped by the app's shutdown is due again at the next start (it uses one of the three). An attempt left `running` with no attempt left (the app ended during the third) is closed as `failed`, `interrupted`. A store's `busy` slot (a Test connection) doesn't use an attempt: the night stays due and the next check tries again.
3. **The snapshot table shape:** the brief's proposal, kept (no simpler shape found that still lists exact restore dates per product): `snapshot_night` + `snapshot_state` as changes, with three additions: a product seen again after a night it was **missing** gets a new row even in the same state (otherwise the missing night would read as a restore date); a night that **failed** in between doesn't break a run (it is simply not an `ok` night, so not a restore date); and `variations_json` for variable products. 30 days × 2 stores at today's data is about 4,800 rows plus one per change, instead of about 144,000.
4. **The snapshot brings the catalog up to date** (the brief didn't say whether it writes `store_product`): a catalog product in the trash gets `status = trash` and `gone_at`; one missing from the listing gets `gone_at`; changed slugs, types, statuses, downloads and meta are saved; titles are kept (the snapshot's `_fields` has no `name`) and **new products are left to the incrementals**. Without this the catalog would keep a trashed product present until a full read (incrementals never see the trash), and each night would report the same differences again. So every change is reported once, by the save that first saw it. `deleted` is reported for a missing product that was present, or was seen on the store's previous `ok` night (so a product a full read had marked gone, then deleted, is still reported once).
5. **The `include_status` probe:** one extra one-row request per night tells a store that knows `include_status` from one that ignores it (an unknown parameter is ignored by WordPress, so such a store would silently list no trash); the main listing is then checked against the probe's trash count. Not verified on a store (V28).
6. **Retention counting:** `snapshot_retention_days` nights are kept counting the night just saved (30: tonight and the 29 before); state rows whose `last_night` is older go, a row still reaching a kept night stays whole. Applied at each successful snapshot (lowering the setting takes effect at the next night).
7. **The watermark guard:** a store date more than a day ahead of the PC's clock never becomes the watermark (a wrong store clock or a hostile answer would otherwise hide every later edit from the incrementals; the nightly snapshot still reads such a product). The PC's clock is only this guard, never a source.
8. **Variations:** at most 4 pages (400 variations) per variable product (`too_many_pages` beyond), stored in the parent's state row; variations aren't in the catalog (m3.1 has no variation slots; V30 says none on the live stores).
9. **The two settings in `PUT /api/settings/app` are optional** (null or absent: kept): the m2 screen sends the five only (`frontend/src/api/settings.ts` `valuesOf`). They are left out of `model_dump` (`Field(exclude=True)`) because the backup import's `ImportedSettings` is built on `AppSettingsValues` and writes `model_dump()`: without that, importing a file exported before m3.2 would fail. Exports now carry the two (`SETTINGS_KEYS` comes from `DEFAULTS`); an import keeps the current values. `validators_for` now builds each validator from the field's type and constraints only (so `exclude` doesn't reach a `TypeAdapter`, which warned).
10. **The scheduled incremental waits one interval after the app starts** (not at once), and the night's catch-up runs at the first check after a start.
11. **A night for a store with no full read is `skipped` (`no_catalog`)**: a store added during the day gets its first night the next night.
