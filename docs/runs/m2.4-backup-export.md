# M2.4: backup export and import

## 1. Brief

### PRD IDs
SET-05 ("Export/import settings + catalog as one file (secrets only with a passphrase)"). The catalog arrives in M3, so `catalog` is `null` in format version 1. The screen is m2.5b.

### Agent and skills
- **`builder`:** Sonnet 5.5 at high, in its own worktree, after m2.1, m2.2 and m2.3 are merged. It never pushes. Context7 for cryptography's `AESGCM` (tag placement, nonce size, size limits) and Python's `hashlib.scrypt`.
- **Don't load** `code-review` or `security-review`.

### Decided already (don't change)
- **KDF** ([11](../11-decisions.md) 2026-10-25, 04 §2, 06 §7, 04-A V21): the standard library's `hashlib.scrypt(password=NFC(passphrase).encode("utf-8"), salt=<16 random bytes>, n=2**17, r=8, p=1, maxmem=256*1024*1024, dklen=32)`. Not cryptography's Scrypt.
- **Cipher:** AES-256-GCM from `cryptography.hazmat.primitives.ciphers.aead.AESGCM`, a 12-byte random nonce, a new salt and nonce for every export.

### What to build
Follow [m2.0-plan.md](m2.0-plan.md) §1 "m2.4-backup-export" exactly:
1. **`secure/backup_crypto.py`:** pure `seal(payload_bytes, passphrase) -> envelope` and `open(envelope, passphrase) -> payload_bytes`, no I/O.
2. **The `.ssbak` file**, UTF-8 JSON: `{"format":"shelfsync-export","version":1,"created_at":<UTC ISO>,"app_version","schema":<highest migration>,"encryption": null | {"cipher":"AES-256-GCM","kdf":"scrypt","n":131072,"r":8,"p":1,"salt":<b64>,"nonce":<b64>}, …}` plus `payload` and `sha256` (hex of the canonical payload; corruption check only) when unencrypted, or `ciphertext` (b64) when encrypted.
   - **AAD** = the canonical JSON (`sort_keys=True`, `separators=(",",":")`, `ensure_ascii=True`) of every header field except `ciphertext`.
   - Import accepts **only** `n=131072, r=8, p=1` for version 1: costs are never taken from the file, and a raised cost is refused before any derivation.
   - Duplicate JSON keys refused (`object_pairs_hook`), unknown fields refused.
3. **Payload v1** (`db/export.py`): `{"settings": {every setting key}, "stores": [{code, name, url, shape, color, spacing_ms, main_button, state}], "storage": {the m2.3 settings}, "catalog": null, "secrets": {"stores": {"<code>": {consumer_key, consumer_secret}}, "s3": {the four}, "github_token": <str|null>}}`. `secrets` appears **only** in encrypted files. The install token is **never** exported.
4. **Passphrase:** 12–1024 characters after NFC, never logged, registered with `redact` for the request's life.
5. **API `api/backup.py`** (behind the guard, in the route walk):
   - `POST /api/backup/export` `{passphrase: str | null}` → 200 `application/json`, `Content-Disposition: attachment; filename="shelfsync-export-<local date YYYY-MM-DD>.ssbak"`; 409 `busy` (one KDF at a time, process-wide).
   - `POST /api/backup/import` `{file: str (the file's text, ≤ 32 MiB), passphrase: str | null}` → 200 `{stores, settings, secrets}` (counts); 422 `export_invalid`, `passphrase_required`, `wrong_passphrase`; 409 `export_too_new` (a newer format version or schema), `import_needs_empty` (the install already has a live store: import is only for a fresh install or a new PC), `busy`; 503 `secrets_unavailable`.
   - Check the request body size limit the app enforces today (the guard or uvicorn); raise it for this route only if needed, and say how.
6. **Import order:** size cap → parse → header check → decrypt and check the tag (or the SHA-256) → validate the whole payload with the same Pydantic models the settings and store APIs use → **only then** one DB transaction, with the Credential Manager writes before the commit; on any failure roll back and delete the entries already written. Imported store secrets are registered with `redact`.
7. **Strings:** proposed 13 wording in the report (the mockup has "Can't open shelfsync-export.ssbak: the passphrase doesn't match." + "Nothing was imported.").

### Tests (07 §1 "Backup")
Round trip with and without a passphrase (the real scrypt parameters at least once; others may patch the cost through a test-only seam that production code can't reach); a wrong passphrase fails cleanly and changes nothing; tampered ciphertext, header, AAD, salt, nonce or KDF parameters fail; raised KDF costs refused before any derivation (assert scrypt isn't called); a plain file holding `secrets` refused; oversize, unknown version, newer schema, duplicate keys refused; the install token never in an export; the passphrase never in a log (`test_never_logged.py`); a failure halfway (a fake secret store failing mid-import) leaves no row and no entry; `import_needs_empty`; `busy`; the guard and the route walk. hypothesis: any single-byte change to the ciphertext fails.

### Request body limit
**Nothing limited a request body before this task**: uvicorn 0.54.0 has no body limit (`h11_max_incomplete_event_size` bounds the request line and headers only; `ws_max_size` is for WebSockets) and FastAPI reads a JSON body whole, so a 32 MiB cap checked after parsing would not have protected memory. I added a pure ASGI middleware, `secure/body_limit.py`, for **two routes only**: `POST /api/backup/import` (body at most `2 * 32 MiB + 64 KiB`, since JSON escaping can double a file text) and `POST /api/backup/export` (64 KiB). It requires exactly one `Content-Length` of plain digits within the limit; a chunked body (no length), a repeated or malformed length, or a bigger one is answered before the app sees a byte, with the route's fixed error (import: 422 `export_invalid`; export: 422 `invalid_request`). A second line stops handing the app bytes past the limit. The guard runs outside it, so a request without a session is 401 first. The file text itself (up to 32 MiB characters) is then checked by the service: longer is 422 `export_invalid`. Every other route is untouched.

### Decisions I took inside the brief (for the lead to record in 11 as Lead (proposed))
1. **`settings` and `storage` don't overlap.** The brief says `settings` is "every setting key" and `storage` is "the m2.3 settings"; read literally the five storage keys would be in the file twice. `settings` holds the seven other keys (`port`, `theme`, `start_with_windows`, `notifications`, `log_retention_days`, `db_backups_kept`, `snapshot_retention_days`) and `storage` the five; a test pins that together they are exactly `DEFAULTS`, so a new setting fails a test until it is placed.
2. **`secrets.s3` is `{rw: {access_key_id, secret_access_key} | null, ro: … | null}`** (a pair, validated by M2.3's `KeyPairRequest`) rather than four loose fields.
3. **An import adds, it never deletes.** A `null` S3 pair or `github_token` in the file leaves the entry already there; a store with no keys in the file is imported without keys (it tests as `keys_missing`). On a failure the earlier S3 and token entries are **put back** (the brief says delete the entries written; this is the same when none was there before). New stores' entries are deleted.
4. **On export, a secret that isn't in the shape the import requires is left out** (with a log line naming no value), so an export can never produce a file the import refuses. A store with only one half of a pair is left out.
5. **A passphrase given for a plain file is ignored** (the owner typed one for nothing); a plain file with `secrets` and an encrypted file without them are `export_invalid`.
6. **Limits:** at most 50 stores; store codes and addresses must be unique inside the file; `secrets.stores` may only name stores in the file; `catalog` must be `null`; `app_version` 1 to 64 printable characters; `created_at` in the `to_iso` shape.
7. **The body limit** (above): requiring a `Content-Length` refuses a chunked import. A browser `fetch` with a string body always sends one.
8. **`temporary_secret(value, minimum=12)`**: the registry's own minimum (16) would not mask a 12- to 15-character passphrase, so the passphrase asks for 12. Other callers are unchanged.
9. **No pre-check of `import_needs_empty` before decrypting**: the brief's order is followed exactly, so a wrong passphrase on an install that has a store is `wrong_passphrase`; the one check is inside the transaction, under the lock.
10. The export reads settings, stores, schema and secrets under `StorageService`'s lock (a consistent file, never half of a key replacement); the derivation and the encryption run **outside** it.
11. `exports=` is the new `create_app` argument; the default is an in-memory service like its siblings.
12. The `ErrorCode`s were appended in `secure/headers.py`; the client's list in `frontend/src/api/client.ts` had to follow (see "Files changed").

### Not verified
- The embedded Python's OpenSSL with `hashlib.scrypt(…, maxmem=256 MiB)`: the probe is in `smoke.py` but only the dev Python ran it. The lead's `release-build.ps1` is the proof (R6).
- A real browser download of the file (Blob, `Content-Disposition`) under the CSP and the file picker's `File.text()` (m2.5b, R8). The body limit was tested at the ASGI level and through `TestClient`, not through a real uvicorn socket with a real chunked request.
- Time and memory of the real scrypt (N = 2**17, about 128 MiB) on this PC under load: the real-parameter tests passed, but nothing measured. Two requests at once are `busy`, never queued.
- The `-m windows` test ran inside the Claude app, not in Windows PowerShell outside it.
- A 12- to 15-character passphrase is masked by value only while its request runs; nothing logs it at all (tested with `redact` off), but if some future code did, only that window is covered. Python strings can't be wiped, so the passphrase and the decrypted payload stay in memory until the collector frees them.
- An imported GitHub token doesn't clear the cached token expiry (`update/state.json`); the next update check refreshes it. `start_with_windows` and `log_retention_days` imported from a file are stored, and take effect at the next start (the screen text says to restart).
- An import into a database being written by another process could wait up to the 5-second busy timeout and then fail with a 500; not exercised.

2. Should `port` be imported at all? The brief says every setting; a new PC may have a different free port (the app falls back to the next free one and says so), so I left it in.

**Lock-order check (R7).** The locks the touched services take: `SECRETS_WRITE_LOCK` (new, re-entrant); SQLite's write lock (`BEGIN IMMEDIATE`, 5 s busy timeout); `StoreService._busy_lock` (a few lines long, never held while another lock is taken; `_claim` marks a store busy, it isn't a lock); `StateStore._lock` (leaf: its callers pass small lambdas); `UpdateService._action_lock` and `_check_lock` (never held around a secrets write); the backup's `_KDF_SLOT` (a non-blocking try, released before the write). The order everywhere is **secrets lock first, then the database's write lock**: `StoreService` now takes the secrets lock before `BEGIN IMMEDIATE` (it used to open the transaction first), the import takes it before `BEGIN IMMEDIATE`, and the export only opens a read transaction. Nothing takes the database's write lock and then the secrets lock. `_KDF_SLOT` and the secrets lock are never held together (the import releases the slot before it writes; the export reads before it derives). Reads of Credential Manager (`get`, the masks, `pair`, a store's Test) take no lock: a Test of a store whose keys are being saved is already `busy` through `_claim`. Found nothing that can deadlock; the concurrency test above would hang on one. Not covered: `InstallToken` (its own entry, not exported, written outside the lock) and the uninstaller (another process).
