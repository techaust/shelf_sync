### What to build
Follow [m2.0-plan.md](m2.0-plan.md) §1 "m2.2-db-backups" exactly. In short:
1. **`db/daily.py`:** the scheduler and the backup.
   - Due at **02:00 Windows local time**; a missed run is caught up at the next start or wake; the loop checks the wall clock every 60 s (`Event.wait(60)`), so a sleep is noticed. Local time from `datetime.astimezone()` (`tzdata` isn't locked, so no `zoneinfo`). The last backup time comes from the newest file name: no state is stored.
   - File `backups\daily-YYYYMMDDTHHMMSSZ.db` (UTC in the name): an online backup on the scheduler's own connection into `….db.part`, then `PRAGMA journal_mode=DELETE` and `integrity_check`, then `os.replace`. Reuse `db/backup.py`'s `_write_checked_copy` (refactor it to be shared if needed; keep its tests green). Stray `daily-*.db.part` files are removed at start through `paths.remove_entry`.
   - Failures are logged (no paths that hold secrets; none do) and retried at the next due time; the app keeps running.
2. **Retention:** deletes **only** plain files (links never followed) whose names match `^daily-\d{8}T\d{6}Z\.db$`, sorted by the time in the name, keeping the newest `db_backups_kept`. It runs only **after** a new backup has passed its check, and at once when the setting is lowered. `pre-migration-*`, `pre-rollback-*`, and any file named by `update\state.json` (checked by resolved path too) are never touched.
3. **Settings** in `db/settings.py`: `db_backups_kept` (default 7, 1–30) and `snapshot_retention_days` (default 30, 1–365; stored only, used in M3).
4. **API `api/backup_settings.py`** (behind the guard, in the route walk): `GET /api/settings/backup` → `{db_backups_kept, snapshot_retention_days, last_backup_at, last_backup_bytes, next_backup_at, daily_count}` (UTC ISO times); `PUT /api/settings/backup` takes the two settings (all required, unknown fields refused, typed with Pydantic) and answers what was saved.
5. **Restore command `python -m shelfsync.db.restore [--list | <file name>]`:** refuses while ShelfSync runs (`default_instance_lock`); takes a `take_snapshot` copy first; accepts only a bare file name of a `daily-`, `pre-migration-` or `pre-rollback-` file directly inside `backups\` (no path, no `..`, no link); refuses a database whose schema is newer than this app knows; reuses `restore_backup` (its allowed prefixes gain `daily-`). Plain messages and exit codes; propose the wording.
6. **Strings:** every new owner-facing string with proposed 13 wording in the report.

### Behaviour worth knowing
- Due = newest `daily-*` file's UTC time is older than the latest 02:00 local that has passed. **A database with no daily backup yet is due at once** (first backup at the first start, not "tonight at 02:00"): otherwise a PC that is off at every 02:00 would never get one. The mockup line "The first runs tonight at 02:00" is then slightly off for the very first run; your call.
- A failed run is not retried each minute: the slot is remembered in memory and tried again at the next 02:00 or the next start.
- Retention counts only plain files with an exact `daily-<stamp>.db` name (a hard-linked file, a link, a folder, an impossible date, `.part`/`.bak` all ignored and never deleted). A file `state.json` names is skipped by path and by resolved path (it still counts toward the number kept).
- The PUT prunes at once only when `db_backups_kept` goes down. Raising never deletes.
- Restore command exit codes: 0 done/list, 1 wrong use or file refused, 2 ShelfSync running, 3 failed (database as it was), 4 data folder or lock unusable. A snapshot `pre-rollback-restore-<UTC>.db` is taken first; if the current database is too damaged to open, its raw file is kept as `pre-rollback-damaged-<UTC>.db` (my addition: otherwise a restore of a corrupt database, the main reason to restore, would be refused), and no database at all means no snapshot.
- Scheduler stop: `join` waits at most 2 s; a backup still running finishes on its daemon thread, and its `.part` is removed at the next start.
