# m3.1: read the stores' catalogs and link them

The first task of M3 ([m3.0](m3.0-plan.md) §1, whose §3 the owner answered on 2026-11-17, all recommended). It reads every downloadable product from every store, read-only, and builds the catalog: items linked by slug, near-miss suggestions found, download slots. It also gives the owner the dry-read command for L1, the first live read.

### What to build

**1. Migration `0003_catalog.sql`** (04 §4; amend 04's rows in your report, the lead updates 04 in m3.6):
- `store_product`: the store's mirror, **only the fields fetched**: store_id, wc_id, slug, title, type, status, modified_gmt, `downloads_json` (each download's id, name and file only), `meta_json` (only the meta entries whose key starts with `latest_version`; nothing else from `meta_data` is kept), seen_at, `gone_at` (set when a full read no longer returns it; never deleted, m3.2/m3.3 use it). Unique (store_id, wc_id); index (store_id, slug). No description, price or any other field.
- `catalog_item`: id, canonical_slug (**nullable**, unique when set: a draft with an empty slug gets an item with no slug and is never linked by slug), title, type, created_at.
- `item_link`: catalog_item_id, store_id, wc_id; unique (store_id, wc_id).
- `slot` (id, catalog_item_id, name, is_main, slug) and `slot_download` (slot_id, store_id, wc_download_id, file_url).
- `sync_state`, one row per store: last full read (started, finished, result reason or null, products read, `X-WP-Total`), `failures_in_row`, `auto_paused_at`, `auto_pause_reason`. (m3.2 adds its watermark in 0004.)
- `wizard` (04 §4: step, state_json).
- Every text column with a length `CHECK` where a hostile store could send something huge; foreign keys on.

**2. The paged reader** (in `apply/`: a new module next to `woocommerce.py`, which is changed only as below):
- `WooClient.get` gains a per-call body cap; the default stays 1 MiB so Test connection is unchanged. Catalog pages use **8 MiB** (Lead (proposed); L1 measures the real page size).
- **Cookies:** no cookie is kept and no cookie text reaches a log. Drop `Set-Cookie` (and `Set-Cookie2`) from every answer at the transport, before httpx's cookie jar parses it, so the `http.cookiejar` warning (t8's side note) can't carry a store's cookie text into the app log through `logging.captureWarnings`. Prove it with a test that sends a hostile `Set-Cookie` and checks the jar stays empty and no log line or warning appears. (This applies to Test connection too.) Check with Context7 that a transport may edit a response's headers in httpx 0.28.1.
- **The listing:** `GET /wp-json/wc/v3/products` with `downloadable=true`, `status=any`, `orderby=id`, `order=asc`, `per_page=100`, `page=1…N`, `_fields=id,slug,name,type,status,date_modified_gmt,downloads,meta_data`. N comes from page 1's `X-WP-TotalPages`; more than **40** pages is refused (`too_many_pages`) before page 2. Before page 1, the `system_status` request Test connection already makes: below WooCommerce **5.8** the store is refused (`wc_too_old`, ERR-02).
- **Spacing:** the store's `spacing_ms` between any two requests to it (APL-12), and a caller can ask for more (the L1 command uses at least 1,000 ms).
- **Retries (APL-12):** 429, 5xx and 520–527 (the reasons `rate_limited`, `cloudflare_52x`, `server_error`, and `blocked` when it came as a 503) are retried up to **3** times, waiting 2, 4, 8 s, or the `Retry-After` (seconds or an HTTP date) when it's given, never more than 60 s. **`timeout` and `unreachable` on a GET are retried the same way** (Lead (proposed): a GET changes nothing, and one slow page shouldn't fail a 25-page read). Nothing else is retried (keys refused, forbidden, redirected, TLS, bad answer). **Only GETs are ever retried:** a test proves the retry code refuses any other method.
- **10 failures in a row** (every failed attempt counts, a success resets the count; kept in `sync_state` across runs) auto-pauses the store's sync: `auto_paused_at` and the reason are set, its later reads are skipped, and it stays so until the owner resumes it. It doesn't change `store.state` (the owner's pause): an auto-paused store **holds updates** from M5 ([11](../11-decisions.md) 2026-11-17, M3 Q3).
- **The count check:** the rows read must equal page 1's `X-WP-Total`, with no id seen twice and every page in ascending id order. If not, the whole listing is read once more; if it still doesn't match, the read fails (`count_mismatch`) and nothing is saved.
- **A bound per store:** 10 minutes for its whole read; past it, `timeout`.
- **Hostile answers fail closed, never crash:** a page that isn't a JSON list, a row without an integer `id`, wrong types, an over-long field (set limits: say which), a bad `X-WP-Total` or `X-WP-TotalPages` all end the read with `bad_response` and save nothing. Titles are stored with `html.unescape` applied (an entity-encoded title is a test).
- **Logs:** one line per store per read: its code, the outcome reason, pages, rows, and the HTTP status of the last failure. Never an address, key, cookie, query string, header or body. New reasons (`too_many_pages`, `count_mismatch`, `no_products`, `auto_paused`, `stopped`) are fixed words like the existing ones.

**3. Building the catalog** (pure functions in a new `backend/shelfsync/catalog/` package, all unit-tested without a database or network):
- **One store's read is saved in one transaction** after it has fully succeeded: rows upserted, rows not returned get `gone_at`; a failed or stopped read changes nothing for that store.
- **Linking (CAT-02):** an item is identified by its links (`item_link` by store and WooCommerce id), so ids, the owner's slug edits and later decisions survive every re-read. A product not yet linked joins the item that already has a product with the **same URL slug** on another store and none on this one; otherwise it gets a new item whose `canonical_slug` is its slug (if that canonical slug is taken, by an owner's edit, say what you do and test it). A product's slug changing later doesn't move its link (m3.3 reports it). Trashed slugs (`<slug>__trashed`) and empty slugs are never linked.
- **Near misses (CAT-03, detection):** among products present on one store only, a pair across two stores is a candidate when the slugs are within edit distance 2 or differ only by WordPress's `-N` suffix, **and** their normalised titles are equal. Normalised title: `html.unescape`, Unicode NFKC, casefold, punctuation to spaces, spaces collapsed. **Edition words are kept** ("X Pro" and "X" are different products; m3.0 correction 7). Candidates are returned, never linked. The 3 pairs of 01-A §2 are a test (their slugs and made-up titles), and so are near-identical slugs with different titles (not candidates).
- **Slots (CAT-05):** the main slot is the download whose name equals the store's `main_button`; when no download has that name and the product has exactly one download, that one is the main slot (Lead (proposed): say in the report how often L1 finds it). Other downloads are extra slots, paired across an item's stores by their exact name. Each `slot_download` keeps the store's WooCommerce download id and file.
- **ERR-02:** a store that returns 0 downloadable products fails with `no_products`, and one below 5.8 with `wc_too_old`, so the wizard can stop at that store with the reason.

**4. The background runner:** one run at a time over all active stores, **one store after another**, never two at once; nothing runs inside a request. It keeps its progress (store, page of pages, rows) for `GET /sync`, and stops between requests and during waits when the app shuts down (the lifespan), leaving that store's old data as it was. A paused (`state='paused'`) or auto-paused store is skipped and shown as such.

**5. The API** (prefix `/api`, same session and security rules as the existing routers; each in its own router module, and `api/app.py` gets only your `include_router` lines and `create_app` keywords):
- `POST /sync`: starts a full read (in m3.1 this is also the wizard's "Build catalog"; m3.2 makes it incremental once a catalog exists). 202 when started, 409 with an error code when one is already running.
- `GET /sync`: running or idle, progress, and per store: last read time, result reason, rows and `X-WP-Total`, failures in a row, auto-paused (and why).
- `POST /sync/stores/{id}/resume`: clears an auto-pause.
- `GET /catalog`: every item in one answer (2,402 is fine; the screen searches in the browser): id, canonical slug, title, type, its links per store (store id, WooCommerce id, slug, status, gone), its slot count, and whether it's linked on every active store.
- `GET /catalog/{id}`: one item with its links, slots and slot downloads.
- `PATCH /catalog/{id}`: the canonical slug only (CAT-04): lowercase `a-z`, `0-9` and `-`, 1–200 characters, no leading or trailing `-`; a slug already in use is a 409. It changes nothing on any store.
- `GET /wizard` and `PUT /wizard/{step}` (04 §5): the steps up to the catalog (stores, storage, test, catalog); an install that already has stores starts at its first unfinished step. Say how each step's "done" is decided (from real state where possible, such as a store saved or a catalog built).
- New error codes appended to `ErrorCode` (the lead merges with later tasks).
- Regenerate `frontend/src/api/schema.d.ts` (`npm run schema` in `frontend/`).

**6. `python -m shelfsync.catalog.report`, the L1 dry read** (run later by the owner in Windows PowerShell outside Claude, 04-A V36, after the owner's go-ahead; [m3.0](m3.0-plan.md) §2):
- reads the real data folder's stores (the database opened **read-only**) and their keys from Credential Manager; reads every active store one after another with the same reader, at least **1,000 ms** between requests (`--spacing-ms`, never lower), the limits above, and `--store <code>` to read one;
- **saves nothing:** no database write, no file, no app log file (console only);
- prints **counts only**, per store and across stores, exactly the list in [m3.0](m3.0-plan.md) §2 ("What L1 prints"), plus the main slot found by the one-download rule, and the largest page in bytes. No slug, title, address, key or file name is printed;
- before any request it prints the requests it will make (paths and parameters, never the address) and waits for Enter; `--yes` skips the wait for a script.
- Tested against fakes only. **Never run it against the live stores.**
